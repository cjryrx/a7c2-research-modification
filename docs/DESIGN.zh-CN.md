# 设计说明：为什么这是「写一条设置」，不是「刷固件」

> 目标：把某个按键绑到「连拍速度提升（Cnt Sht Spd Bst，保持/切换）」。
> 结论：绑定是**相机可写区里的一条 4 字节设置**，不是固件里的代码或资源。
> 所以本工具只做 AP 属性的读/写/保存，一个字节的固件都不碰。

## 1. 一句话原理

```
自定义键绑定 = AP 属性组 0x02CF 里的一个 4 字节槽位
              槽位 index 0x0404 … 0x041F
              值 = 4 字节小端「紧凑功能 id」（如 0x300 = APS-C/全幅选择）
app 启动时把槽位读进内存 → 按键分派到对应功能
```

因此改绑 = 写 4 个字节 + `saveBackup(0x02CF)`，然后**断电重启**让 app 重新读取。
没有代码补丁、没有 DAT 重打包、没有分区写入。

## 2. 这个值存在哪里

| 项 | 值 | 说明 |
| --- | --- | --- |
| 组（group / subsystem） | `0x02CF` | 属性键高 16 位 |
| 槽位 index | `0x0404 … 0x041F` | 属性键低 16 位；连续 28 个 4 字节槽位 |
| 属性键 | `0x02CF0000 \| index` | 例：AF-ON = `0x02CF041B` |
| 值编码 | 4 字节**小端**紧凑 id | `0x300` → 字节 `00 03 00 00` |
| 已验证槽位 | `0x041B` = AF-ON，`0x041C` = MOVIE | 端到端写 + 重启验证 |
| 持久化 | `writeBackup(key, bytes)` + `saveBackup(0x02CF)` | 回读确认；重启后仍在 |
| 生效时机 | **机身断电重启之后** | app 只在启动时读取绑定 |

「小端」是怎么确定的：全组差分里 MOVIE 槽的两条原始记录是
`05030000 -> 00030000`，而对应的两次菜单选择是「切换静音模式」与「APS-C/全幅选择」；
同一份差分里 AF-ON 的槽是 `c3090000 -> 22010000`，对应 `0x9C3 -> 0x122`。
只有按小端解释，这些数值才与已知的紧凑 id 表一致。

## 3. 证据表

下表每一行都是真机上做过的测量；「强度」列区分**端到端**、**差分**与**推断**。

| # | 测量 / 实验 | 结果 | 能推出什么 | 强度 |
| --- | --- | --- | --- | --- |
| 1 | 在机身菜单里改 AF-ON（跟踪+中央 AF → 对焦模式）和 MOVIE（切换静音 → APS-C/全幅），前后各读 1024 个属性（`0x300–0x6FF`）做差分 | 只有 `0x02CF041B`、`0x02CF041C` 变化 | 绑定落在这两个槽位，不落在那 1 字节的自定义键属性组里 | 差分 |
| 2 | 再把 MOVIE 从 APS-C 改回静音，前后各抓 `0x02CF` **全组 6553 项**做差分 | 只有 `0x02CF041C` 一项变化 | 全组范围内没有第二个候选；绑定就是槽位本身 | 差分 |
| 3 | 把两份差分里「原值 → 新值」与用户实际下的菜单命令对齐 | `0x9C3 → 0x122`（AF-ON，→ 对焦模式）、`0x305 → 0x300`（MOVIE，→ APS-C） | 槽位值 = **紧凑功能 id**，与 FUNC/EVENT id 不是同一套编号 | 推断（与 #5 合并后成立） |
| 4 | 把 1 字节的自定义键属性 `0x02CF0539`（AF-ON 槽位标识）从 `0a` 写成 `02` 并 save | 按键行为不变 | 那组 1 字节值只是**物理按键槽位描述**，不是功能绑定 | 端到端 |
| 5 | 写 `0x02CF041B = 0x300`（APS-C）并 `saveBackup(0x02CF)`，**不重启** | AF-ON 仍然是「对焦模式」 | 写入 + save 立即生效于属性值，但 app 不会重新读取 | 端到端 |
| 6 | 同上再**关机 → 开机**，按 AF-ON | AF-ON 执行「APS-C/全幅选择」（用户确认） | `0x02CF041B` 就是 AF-ON 的绑定槽；app 只在启动时读取；改绑不需要改固件 | **端到端（决定性）** |
| 7 | 每次写入后立刻 `readBackup`，`saveBackup` 后再读一次 | 两次都等于新值 | 写路径与 save 命令都被服务接受；回读不一致时工具必须报错 | 端到端 |

实验结束后已把 `0x041B` 写回 `0x00000122`（对焦模式）、`0x0539` 写回 `0x0a`，均回读确认。

## 4. 为什么不是「固件补丁」

| | 固件/DAT 补丁路线（本项目的前置工作） | 本工具 |
| --- | --- | --- |
| 改动对象 | `appFw.so` / DAT 里的代码或资源、CP/BK4 属性 | 一条 4 字节 AP 属性 |
| 需要的材料 | 官方 DAT、updater 密钥、重打包、版本门控 | 相机 + USB 线 |
| 失败模式 | 版本不匹配、校验失败、机身无法正常启动 | 按键绑成别的功能；可写回 |
| 可逆性 | 需要重新打包/刷回 | 写回 4 字节 + save + 重启 |
| 是否需要动分区 | 是（写 flash 区域） | 否（`writeBackup`/`saveBackup` 是服务命令） |
| 本仓库是否包含固件 | — | **否**：没有 DAT、没有 `appFw.so`、没有分区转储、没有抓包、没有序列号 |

「连拍速度提升」的困境也正因如此：机身菜单的可分配功能列表里**没有**这一项
（菜单数据在固件资源里），但**绑定槽位并不校验菜单**。
所以最短路径不是改菜单数据，而是直接往槽位写那个功能的紧凑 id。

## 5. 工具如何把风险压到最低

1. **范围限制**：只读写 `0x02CF` 组；`bind` 只允许 `0x0400–0x0430`，超出直接拒绝（`--force` 也不放行）。
2. **长度守卫**（最关键的一条）：写入前先读当前值，**新值长度必须与当前长度完全一致**，
   否则拒绝。属性记录是整条替换的，长度不符会改写记录边界——这是唯一可能造成结构性损坏的操作，
   所以它在代码里是硬约束（[`check_write`](../bind_button/properties.py)）。
3. **回执先落盘**：`bind` 在动相机之前先把旧值写成 JSON 回执（`receipts/`），
   任何一步失败都能用 `restore --receipt` 原样写回。
4. **只写 4 字节 + 只 save 一个组**：没有批量写、没有循环写、没有"猜值"。
5. **不做的事**：不写文件到相机存储、不发送文件控制/内存转储命令、不碰固件更新通道、
   不读取或记录序列号（`ProductInfo` 只校验长度，内容既不保存也不打印）。
6. **失败即停**：写入后回读不一致、save 后回读不一致，都直接报错并保留回执，不继续重试。

## 6. 仍然未知 / 未验证

诚实地列在这里，避免读者把推断当结论：

| 项 | 状态 |
| --- | --- |
| 「连拍速度提升（保持/切换）」的紧凑 id | **未知**。这是唯一的缺口，工具因此把 id 作为参数，并在代码与文档里都不写猜测值。 |
| app 的功能分派是否接受「菜单里没有」的 id | **未验证**。0x300 的端到端实验只证明菜单内已有的功能可行；若分派层有白名单，写入未知 id 后按键可能无反应。 |
| 每个槽位对应哪个物理按键 | 只有 `0x041B` = AF-ON、`0x041C` = MOVIE 是验证过的；其余槽位只知道"在绑定区内"。`discover` 子命令就是为此准备的。 |
| `0x0420–0x0430` 是否也是绑定槽 | **未知**。它们看起来是另一组重复值（`0x35D`），没有验证过，所以写在界外需要 `--force`。 |
| `saveBackup` 的协议级语义 | 只验证了"save + 重启后值仍在、行为改变"；没有固件侧的文档或反汇编证据说明它写到哪一层。 |
| 其他机型 | 未验证。同一代机身可能共用布局，但本仓库只对 ILCE-7CM2 负责。 |
| 紧凑 id ↔ FUNC/EVENT id 的映射表 | 已知 4 组锚点，但离线分析没有找到成表关系（`EVENT_FUNC_CUSTOM_APS_C_SUPER_35MM_SEL_ON=0xb9cd` 等与紧凑 id 无线性关系），所以不能从 FUNC id 推算未知 id。 |

## 7. 为什么这个仓库里没有索尼固件

本工具证明的是"改设置就够了"，所以它**不需要**任何固件材料：

* 不需要官方 DAT、不需要 updater 密钥、不需要 `appFw.so`；
* 不包含任何 DAT/BIN/分区转储/抓包/序列号；
* 全部相机侧效果只有一条 AP 属性 + 一次 group save。

这也是本项目与"固件补丁"路线的分界线：前者交付的是一个可回退的设置写入工具，
后者交付的是改过的固件包。
